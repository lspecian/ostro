**User-review items** (11-01 flags them in STATE.md Pending Todos as `[USER REVIEW]`):
- **D-P11-3 / D-P11-8:** rerun semantics. Effects after the cut really re-execute (new run id → new idempotency keys). Only terminal sources can be rerun. Reruns of child runs are detached.
- **D-P11-13:** the published limit defaults (history 50,000 events, children 10,000 per run, payload 4 MiB) and the "breach = resumable `limit_exceeded` at the next live command" behaviour.
- **D-P11-14:** the UI stack (askama `=0.16.1`, which pulls syn 3, plus vendored htmx 2.0.11). maud 0.27.0 is the fallback.
- **D-P11-17:** UI exposure while auth is off (Phase 14). The UI is on by default in dev. In the server profile it is on only for a loopback listener or an explicit `[ui] enabled = true`.

An override can be folded into any plan that has not started yet. Ordinals already shipped in code follow RESERVATIONS.md rule 3: never reused or renumbered.

## Shared files (cross-phase and intra-phase)

## Commit procedure (every plan)

Executors share one checkout with Phase 9/10 executors. Edits, builds and tests happen in a **scratch worktree under /tmp**, never inside the repo. Commits go through a **private index** in the main checkout and add only the plan's own files (the Phase 10 procedure).

```bash
REPO=<repo>
WT=/tmp/ostro-wt-11-NN                      # once per plan; never inside $REPO
git -C "$REPO" worktree add --detach "$WT" HEAD
base=$(git -C "$REPO" rev-parse HEAD); echo "$base" > "$(git -C "$WT" rev-parse --git-dir)/p11-base"
export CARGO_TARGET_DIR=/tmp/ostro-target-11-NN   # per plan, avoids lock contention between parallel plans
# ... edit, build, test inside "$WT" (all <verify> commands run from "$WT") ...
cd "$REPO"; for f in <own files>; do git diff --quiet "$base" HEAD -- "$f" || echo "MOVED $f"; done   # MOVED → re-apply on the new HEAD first
idx="$(git rev-parse --git-dir)/index-11-NN"; rm -f "$idx"
GIT_INDEX_FILE="$idx" git read-tree HEAD
for f in <this task's files, listed explicitly>; do
  if [ -e "$WT/$f" ]; then mode=100644; [ -x "$WT/$f" ] && mode=100755
    GIT_INDEX_FILE="$idx" git update-index --add --cacheinfo "$mode,$(git hash-object -w -- "$WT/$f"),$f"
  else GIT_INDEX_FILE="$idx" git update-index --force-remove -- "$f"; fi
done
GIT_INDEX_FILE="$idx" git commit -q -F "$msgfile"     # message ends with the Co-Authored-By line
rm -f "$idx"; git reset -q -- <the same files>        # resync the shared index for these paths only
git show --stat HEAD                                   # exactly this task's files
# next task: git -C "$WT" checkout -q --detach "$(git -C "$REPO" rev-parse HEAD)"; refresh p11-base
# end of plan: git -C "$REPO" worktree remove --force "$WT"
```

- zsh does not word-split unquoted variables: use an explicit array or run the loop under `bash`.
- The shared checkout's working tree is never written by an executor (not even `git checkout -- <path>`), so other agents' stale blobs are left alone.
- Never `git add -A`, `git add .`, `git add -u`, `git commit -a`, `git stash` or `git reset --hard`.
- Messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. No remotes, no pushes, tags stay local.
- Never run gsd-tools `state advance-plan`, `roadmap update-plan-progress`, `phase complete` or `requirements mark-complete`.

## Injected clock (every plan, W-2)

- **Rerun (11-07/11-10):** validation moved into `rerun::check(&StartRun)` before any read/write; the re-arm uses the shared `EngineExecutor::prelude` (one call covers embedded and remote runners). A rerun goes through StartRun rate-limit admission. Unsafe-cut CLI scenario uses a past-terminal cut (an open-effect cut needs an egress allow-list in `ostro dev`); the server covers `open_effect`.
- **DLQ/hooks (11-12):** hook and catch-up tests use the system clock with short windows (the guests' sleeps run on the server clock); server logic still reads time only through the injected clock. Hook starts go through StartRun admission; a 429 is retried by the next catch-up.
- **DLQ reason (fixed by 11-18):** a failure message that already starts with its reason code (`limit_exceeded: history_events 21 > 20`) is no longer prefixed twice (`fix(11-12)`).
- **Bulk (11-13):** restart-with-key is a private copy in `services/bulk.rs` (p11_dlq's helper is private); pacing test uses `ManualClock`. A bulk `retry` of a guest failure restarts (new linked run, same tags); the snapshot bound keeps those out of the job. The bulk caps (`[bulk] max_jobs/max_matches/max_rate`) and `MAX_SEARCH_TAGS` are not published limits (not in docs/limits.md or `/v1/limits`).
- **Kill tests (D-P11-32):** 11-07/11-12/11-13 ran their crash tests in-process with the failpoints feature; 11-18 added the spawned failpoint-binary versions (`crates/ostro/tests/ops_kill.rs`). They use the `ostro` binary that `cargo test -p ostro --features failpoints` builds (no separate `--target-dir target/failpoints` build). FAILPOINT_CRATES runs whole test targets (the entry format has no name filter).
- **Replay corpus (11-18):** `export_run` copies `JournalEvent.attempt` (field 4) into `journal.bin`, so the records stay the exact `Events` row bytes; the two `rerun-*` entries are the first that carry it.
- **Clock gate (11-18):** every Phase 11 commit added 0 unexempted `SystemTime::now`/`SystemClock`/`Instant::now` reads (scoped check over all `(11-NN)` commits). The strict CLOCK_GATE (Phase 10's command) still reports 33 pre-existing hits in Phase 2/4/5/6/7/8/9 files; Phase 10's clock-exempt sweep (10-06) has not run, and 11-18 never edits them.
- **Leader-only services (Phase 12/13 coordination):** `dlq_hook::spawn` runs on every started partition slot and bulk jobs run node-locally; both are correct only while every ready slot is the leader (RF1). Once Phase 12 followers exist, `dlq_hook` must run on leader slots only (with the other leader services) and bulk jobs must target leaders / be forwarded (Phase 13, D-P11-20).

Readiness itself is unchanged. The same commit fixes a `bulk_ops` flake: `ostro_bulk_jobs{state}` is an absolute per-registry gauge on a process-global recorder, so parallel in-process servers overwrite it.
