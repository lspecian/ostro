  <files>(no source files; campaign state under target/campaign, report goes to the SUMMARY and 05-VALIDATION.md)</files>
  <action>
1. Build once: `cargo build --release -p ostro --features failpoints --locked`.
2. Run the campaign as 20 shards × 500 faults (`OSTRO_CAMPAIGN_FAULTS=10000 OSTRO_CAMPAIGN_SHARDS=20`), in batches so that each command fits the tool timeout, or in the background:
   - Batch form: `OSTRO_CAMPAIGN_FAULTS=10000 OSTRO_CAMPAIGN_SHARDS=20 OSTRO_CAMPAIGN_SHARD_IDS=<a-b> OSTRO_CAMPAIGN_PARALLEL=6 OSTRO_CAMPAIGN_STATE_DIR=target/campaign cargo test --release -p ostro-crashtest --features failpoints --test server_campaign --locked -- --ignored --nocapture`.
   - Or launch the full run in the background with `nohup … > target/campaign/run.log 2>&1 &` and poll `target/campaign/shard-*.json` until every shard reports `faults_done >= 500`. The runner is resumable: re-running a batch continues from the persisted state.

   - total counted faults ≥ 10,000, broken down by kill / failpoint / ENOSPC;
   - lost acked runs = 0;
   - duplicate journal entries = 0;
   - all runs terminal or resumed.

   Paste the report table and the wall time into the SUMMARY.
4. Any invariant violation is a real durability bug. STOP: do not freeze. Report the shard, seed and failing run, and keep `target/campaign` for diagnosis. The orchestrator then plans gap closure.

  </action>
