  <files>crates/ostro-engine/src/replay/wait.rs, crates/ostro-engine/src/replay/cursor.rs, crates/ostro-engine/src/replay/mod.rs, crates/ostro-engine/src/host/effects.rs, crates/ostro-engine/src/replay/tests.rs</files>
  <behavior>
    - Unit cases:
      - a cancelled sleep waited with `All` → `Err(Cancelled)`;
      - input TimerFired at seq 5 then OpCancelled at seq 7 → the op completes Ok(Timer) (input wins);
      - OpCancelled at seq 5 then TimerFired at seq 7 → `Err(Cancelled)`, and the later input is ignored for that op;
      - a wait-signal op with WaitTimedOut → `Err(Timeout)`;
      - an await-token op with WaitTimedOut → `Err(Timeout)`.
    - `completion_for` uses a `BTreeMap<OpId, u64>` index. The first completion per op wins. The index is filled on load, in `deliver_inputs` and in `append_live` (OpCancelled is a guest command, so it is appended live). A test builds a 50k-event journal and asserts lookups do not scan.
    - `gather_race_prop` (proptest, 256 cases by default, overridable with `OSTRO_PROP_CASES`) generates:
      - N ops (sleep, signal, token);
      - a random arrival order of completion inputs, including WaitTimedOut;
      - a random sequence of `wait(All|Any)` and `cancel-op` calls.

      Running live through ReplayState with inputs delivered in that order, then replaying from the produced journal, gives identical `WaitResolved` lists and identical guest-visible results.
  </behavior>

  <behavior>
    - The guests use the Rust SDK and all export workflow `patch-demo` v1:
      - patch-v1: step A, `sleep(2 s)`, step B, returning the list of executed steps;
      - patch-v2: step A, `if ctx.patched("add-c") { step C }`, `ctx.patched("add-c")` called a second time (must return the memo), sleep, step B;
      - patch-v3: v2 with the `patched` call removed and C always executed.
    - v1 journal (complete, and parked mid-sleep) replayed by v2: completes without C, `patched` returns false, no PatchMarker is appended, and there is no NonDeterminism.
    - Fresh v2 run: exactly ONE PatchMarker for "add-c" (memo), C is executed, and the result is [A, C, B].
    - A v2 journal replayed by v3 completes: the unqueried marker is skipped, there is no divergence, and the result is [A, C, B].
    - A v2 journal replayed by v2: zero new events.
  </behavior>
  <action>
Add `patched: BTreeMap<String, bool>` to ReplayState. The first evaluation per change-id decides:
- live: append the marker and return true;
- replay: consume a matching marker at the cursor and return true; otherwise return false.

Later calls return the memo with no journal effect.

Unqueried-marker skip: when matching the next guest command, consume any recorded `PatchMarker`s before it that the code never queried. Markers have no side effects, so this is safe (03-RESEARCH rule). Document the rule in a doc comment that quotes D6.

`patching.rs` drives the guests through the engine testkit with recorded journals, using the `sdk_guests.rs`/`activation.rs` patterns. Add the three guests to the guests workspace; the members glob picks them up.
