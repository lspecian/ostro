  <behavior>
    - `RunWatchers`:
      - one task per partition subscribed to the apply machine's action broadcast;
      - `RunCompleted{run, status}` drains `Mutex<BTreeMap<RunId, Vec<oneshot::Sender<()>>>>`;
      - on `Lagged`, wake every waiter of that partition;
      - empty vectors are removed;
      - a waiter is dropped when its future is dropped (client disconnect); test this with a counter.
    - `await_result`:
      1. register;
      2. read the record; if terminal, return immediately;
      3. otherwise wait for `min(wait, 60 s)`;
      4. re-read and return `{status, completed, result?, failure?}`.

      Always 200 (gRPC OK).
    - `follow_continuations=true` loops while the status is ContinuedAsNew, using `result.next_run_id`, within the same overall deadline.
    - Tests:
      - long-poll on a run that completes after 300 ms returns in < 1 s (not at 30 s);
      - a 200 ms wait on a sleeping run returns `completed: false` in about 200 ms;
      - race test with 200 iterations: completion races registration (complete immediately after start) and no request waits for the full timeout;
      - can-chain with max 3 → follow returns the final run's result;
      - REST and gRPC parity of the response.
  </behavior>
