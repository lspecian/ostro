  <behavior>
    - **RegisterWait is idempotent** (B2: 05-11 re-arms unresolved ops after a resume, and a repeat must be harmless):
      - if the wait row for `(run, op)` already exists, the intent is a no-op: no second timer and no `open_waits` change;
      - if `op ≥ rec.next_seq`, the op does not exist yet → Rejected(Invalid);
      - a RegisterWait whose `timeout_due_ms` is already in the past still inserts its timer row; the timer service fires it on the next tick, which journals WaitTimedOut.
      - Each insert of a new wait row increments `rec.open_waits`; each removal (signal, token, timeout, CancelWait) decrements it.
    - RegisterWait{op, Signal(name), timeout_due_ms}:
      - inserts both wait key shapes, plus timer `(due, run, op)` when due > 0;
      - if the inbox has a slot for `name` (one prefix read), it journals `SignalMatched{op, payload_seq: slot.payload_seq}` immediately (ts = `RegisterWait.at_ms`), deletes that inbox slot and the just-written wait and timer rows, and emits InputAppended. The run is Running, because the intent came from its own executor.
    - RegisterWait{op, Token, due}: inserts the wait row and timer only. Tokens are never buffered.
    - SignalRun:
      - unknown run → RunNotFound; terminal → RunTerminal;
      - **W5:** an inline `event` PayloadRef over 256 KiB → `PayloadTooLarge` (a blob ref is fine);
      - request_id present and in SignalSeen → Duplicate; otherwise insert SignalSeen;
      - **B1, signal before RunStarted:** when `rec.next_seq == 0`, journal nothing. Store `SignalSlot::Pending{event, sent_at_ms}` at `(run, name, inbox_next)`; there is no wake, because the run is already Ready/Scheduled for its first activation. Then stop.
      - first, `journal_encoded(SignalPayload, s.event)` at next_seq (= payload_seq) — verbatim, without waking yet;
      - oldest wait for name present → `journal_input(SignalMatched{op, payload_seq})` at the next seq (ts = sent_at_ms), remove its rows and timer, and wake (Scheduled → Ready + EnqueueReady; Running → InputAppended for both seqs; Ready → nothing);
      - no wait → store the inbox slot `(run, name, inbox_next) → {payload_seq, sent_at_ms}`; the run is not woken (nothing is waiting), but a Running run still gets InputAppended for the SignalPayload seq so its journal view stays contiguous;
      - `s.event` absent → Rejected(Invalid(MissingField)).
    - **`on_first_events` (B1).** Called by run.rs after the seq-0 batch's events are written and before its intents are applied (also after `StartRun.run_started`, from 05-16). For each `Pending` slot of the run, in `(name, n)` order, it calls `journal_encoded(SignalPayload, slot.event)` at next_seq and rewrites the slot to `Journaled{payload_seq, sent_at_ms}`. If any were converted, it emits `InputAppended` (the executor's next append then conflicts and re-activates, the existing Pitfall 2 path). This costs one inbox prefix read, and only when `inbox_next > 0`; assert it.
    - Inbound outbox Signal follows the same logic as SignalRun, including the Pending case and the W5 size limit on its `payload`, with its `payload` field treated as the encoded SignalPayload event bytes (D21), except for dedupe: cross-partition dedupe is the existing `(src, seq)` dedupe.
    - try_wait_timeout(run, op): wait row present → journal WaitTimedOut{op}, remove both wait shapes, delete the timer row, wake, return Some(Accepted). Absent wait row → None (ordinary timer path).
    - CancelWait{op}: removes the wait rows and timer. Absent → no-op inside EventsAppended; the intent never rejects the batch.
    - FIFO tests:
      - two waits on "x" and one signal → the lower op completes;
      - three signals before any wait → consumed in send order by successive RegisterWaits;
      - signal-after-timeout → inbox;
      - timeout-after-signal → no-op, exactly one completion event for the op.
    - Read-count tests for SignalRun (with and without request_id) and RegisterWait. They assert the exact counts.
    - Idempotency tests:
      - RegisterWait twice → one wait row, one timer row, open_waits == 1;
      - RegisterWait with a past due → after TimerFired, WaitTimedOut is journaled once;
      - Apply cannot detect a RegisterWait for an op that was already satisfied (no row, op < next_seq), and it would re-insert the wait. The contract is that the submitter (05-11 re-arm) sends only ops with no completion in the journal. State this in the RegisterWait doc comment, and add a test that documents the behaviour so a future change is deliberate.
    - open_waits tracks the live wait-row count through every path (assert after each scenario).
    - **B1 "signal before first activation" test:**

      - then an EventsAppended from_seq 0 (RunStarted + SignalWaitStarted) with RegisterWait → both SignalPayloads are journaled after the batch's events, and the RegisterWait matches the oldest with SignalMatched;
      - rebuild_digest stays equal;
      - inbound Signal before start behaves the same way.

    - **D21 1 MiB tests:**
