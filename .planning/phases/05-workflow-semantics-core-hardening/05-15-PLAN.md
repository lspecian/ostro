  <behavior>

      - a signal sent afterwards → 200 accepted, and inspect shows it buffered: the run is terminal, so 409 is also acceptable; assert whichever 05-08/05-13 defined and document it;
      - `before` mode: signals sent during the sleep are consumed in FIFO order.
    - `patched_in_flight`:
      - start patch-v1 and wait until it is sleeping;
      - restart the server with `module_override` mapping that run to the patch-v2 sha (module uploaded);
      - the run completes with [A, B] and no C, and its history has no PatchMarker;
      - a fresh run on v2 → [A, C, B] with exactly one PatchMarker.
    - `timeouts`:
      - run_timeout 500 ms on sleep_forever → TimedOut, with history ending in run_terminated reason run_timeout;
      - on busy_steps → TimedOut and the activation revoked (live_activations returns to 0);
      - schedule_to_start 300 ms while the dispatcher is paused, using the mechanism 05-11 added (the `#[doc(hidden)]` dispatcher pause hook through `start_with_hooks`, or `executor.slots = 0`; see the 05-11 SUMMARY) → TimedOut reason schedule_to_start;
      - with capacity → no timeout.
    - `cancel_cleanup`: order-saga at engine level is not available here, so use the crash-saga or wit-surface cancel path. The cleanup step runs and the status is Cancelled.
    - `terminate`: no further guest steps (step count frozen) and the status is Terminated.
    - `resume_after_signal_wait_timeout` (B2a): start signals `long_wait` with run_timeout 300 ms. It becomes TimedOut while waiting. Then:
      - `POST …/retry` → `mode: resumed`, same id;
      - `POST …/signals/x` with payload 7 → the run completes with result 7;
      - history contains SignalMatched (pointing at the SignalPayload event) for the original wait op, and no TimerFired or WaitTimedOut for it.
    - `resume_after_sleep_timeout` (B2b): start timeouts `sleep_ms(800)` with run_timeout 200 ms. It becomes TimedOut while sleeping. Then:
      - wait 1.2 s, so the original sleep due time has passed;
      - retry → resumed → the run completes within 5 s (the re-armed past-due timer fires immediately);
      - inspect shows no new run timeout after the resume.
    - `retry_resume`: a TimedOut run → retry → mode resumed with the same id → completes once run_timeout no longer applies (e.g. busy_steps with a finite count and a resumable timeout). `retry_restart`: a guest-failed run → mode restarted, and the new run has `retry_of`.
    - `signal_immediately_after_start` (B1): start the `signals` guest in `fifo` mode and send 3 signals on `x` right after the start response, before any activation (pause the dispatcher with the 05-11 hook to force it). Unpause → the run completes with the 3 payloads in order. History shows the SignalPayload events after RunStarted, each followed by its SignalMatched.
    - `large_payloads` (D21): a 1 MiB signal payload delivered to a waiting `signals` guest and a 1 MiB token payload delivered to `tokens` both complete, with results byte-identical to what was sent. A server restart followed by a replay of both runs from their journals (blob-backed events) appends zero events.
    - `tokens`: complete → completes with the payload; second → 409; tokens guest with a 200 ms timeout → 409 after expiry.
