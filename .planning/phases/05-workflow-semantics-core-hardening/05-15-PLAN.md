  <behavior>

      - builds or locates the failpoint-enabled release binary (`cargo build --release -p ostro --features failpoints` once per process; path under `target/release/ostro`);
      - spawns `ostro dev --data-dir <dir> --listen 127.0.0.1:<port>` with `FAILPOINTS`, waits until ready, uploads crash-saga and activates it;
      - `kill9()`, `restart()`.
    - `Workload` (reqwest):
      - N concurrent starters with idempotency keys, 10% intentional duplicates;
      - signals "go" and "extra" with request_id, including retries of the same request_id;
      - 5% cancels and 2% terminates;
      - every 2xx is recorded in an `AckLog` (append-only file, fsync per record) as `{kind: start|signal|cancel|terminate, run_id, key, request_id, payload, ts}`.
    - `check`:
      - (a) every acked run exists after restart (GET 200);
      - (b) after the final settle (faults off, pending signals delivered, wait up to T), every acked run is terminal. Completed runs have result == `crash_saga_expected(input, accepted signals)`. Cancelled and terminated runs have the right status, given that a cancel acked after completion is a no-op;
      - (c) journal invariants per run from history (list from the must_haves);
      - (d) `rebuild_and_compare` on a copy every K iterations;
      - (e) acks received just before the kill are not lost (covered by (a)).
    - `check_controls.rs` (default suite, no server): synthetic histories and ack logs with a lost ack, a duplicate StepCompleted, two completions for one op, a duplicate request_id signal and a wrong result. Each must be detected with a specific error.
  </behavior>
