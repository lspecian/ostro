<task type="auto" tdd="true">
  <name>Task 1: Upload and activation gates + effective policy (cluster ∪ tenant tightening) + attach signatures</name>
  <files>crates/ostro-server/src/p14/module_sign.rs, crates/ostro-server/tests/signed_modules.rs</files>
  <behavior>
    - `effective_policy(view, tenant)`: `require = cluster.require_signed_modules || tenant.require_signed_modules == Some(true)` (a tenant `Some(false)` never relaxes); trusted keys = cluster keys ∪ tenant keys (tenant keys apply only to that tenant's uploads).
    - **Order (B1b):** `upload_gate` is called (14-01b call site) right after the sha check and **before the existing-sha lookup, compilation, any meta write and auto-activation**, with the uploading principal's tenant; so a cross-tenant re-upload of an existing sha is gated like a fresh upload.
    - `upload_gate`: parse signatures (14-02 carriage), verify against the effective keys; required + none valid → 403 `signature_required` (no signatures) / 400 `signature_invalid` (signatures present, none valid); not required → still verify any provided signatures and keep valid evidence (invalid provided signatures → 400, so users notice). Returns evidence; the upload path writes it into ModuleRecord ext 113 as `ModuleSig{alg, key_fingerprint = sha256(alg ‖ public_key), key_id, sig, added_at_ms, added_by = token id}` (merge with existing evidence for the same sha) (B1c).
    - `activation_gate` (B1c): if required for the **activating** tenant, load the module bytes from the blob store and `signing::reverify(bytes, ext113.sigs, effective_keys(activating tenant))`: a stored signature counts only if its `key_fingerprint` matches a currently trusted key of that tenant's effective set and it re-verifies over the blob; none → 403 `signature_required`. A removed key, or evidence produced under another tenant's tenant-only key, therefore never satisfies activation.
    - `version_gate` (B1a, W3): called on **every** explicit version/sha selection when enforcement applies to the tenant (fast accept when the target is the active version or its ext 113 evidence re-verifies; no race with a concurrent Activate); paths (start with explicit `version`, `migrate-runs` target, rerun/retry with a version override); runs the same evidence check as `activation_gate` for the target version's module when enforcement applies to the tenant, else Ok; failures → 403 `signature_required`.
    - `attach_signatures(sha, sigs)`: verify against stored bytes, merge evidence.
    - `signed_modules.rs` (single node then tier-B 3 nodes): policy off → unsigned upload OK; turn on (system admin) → unsigned upload 403, bad signature 400, valid minisign (test signer) 200 with evidence; valid cosign keyed 200; a module uploaded unsigned before enforcement → activation 403 → attach signature → activation OK; an already-active unsigned version keeps serving starts and its running runs complete after enforcement is enabled; tenant tightening: cluster off, tenant a on → a's unsigned upload 403, b's OK; removing a trusted key → activation of modules signed only by it 403; 3-node cluster with `[security.modules]` set on node 1 only → uploads through node 3 are still rejected unsigned (policy from meta); a rejected upload leaves no ModuleRecord and no blob reference. **B1 tests:** (a) with enforcement on, `start` with an explicit `version` whose module is unsigned → 403 and no run created; `migrate-runs` (dry_run false) to an unsigned version → 403 and no RepinRun proposed; rerun/retry with an unsigned version override → 403; (b) tenant a uploads module M unsigned before enforcement; enforcement on; tenant b re-uploads the same bytes unsigned → 403 and afterwards **no b WorkflowVersion, no b Active row, no ModuleUploaders change**; (c) evidence whose fingerprint belongs to tenant a's tenant-only key does not let tenant b activate M; replacing a trusted key with another key that has the same minisign key id but a different public key invalidates the evidence.
  </behavior>
