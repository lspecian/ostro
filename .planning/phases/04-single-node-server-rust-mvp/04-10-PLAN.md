  <behavior>
    - retry-probe mode "hang:T" runs a busy loop step with timeout-ms T (e.g. 200 ms) and retry max 2: attempt 1 interrupted -> StepAttemptFailed{failure: Timeout}; attempt 2 interrupted -> StepCompleted(Err(Timeout)); the activation then continues/finishes per guest code; total wall time ≈ 2*T + backoff, far below activation_timeout
    - mode "quick" with timeout-ms 5000 completes normally
    - mode "burn" (step fuel budget small, busy loop) -> step recorded NonRetryable{kind: "fuel_exhausted"}, attempt does NOT end AttemptFailed(FuelExhausted)
    - a busy loop OUTSIDE any step still ends AttemptFailed(Timeout) at activation_timeout (set short in the test config)
  </behavior>
  <action>
Store per-HostState `step_deadline: Option<(seq, Instant)>`. Live `begin_step` with `timeout_ms` sets it to `now + timeout` (wall clock; it only decides live behavior, never journal content beyond the recorded Timeout failure). The epoch callback computes `effective = min(wall_deadline, step_deadline)`; when the step deadline passes, it traps with a dedicated payload `StepTimedOut{seq}` (distinct from the activation timeout). Because a trap unwinds the guest, the step's retry cannot be retry-now'd in place: after unwind, activation.rs records the failure for the open step through the same decide path used in 04-07 (`Timeout` is retryable): SAF (backoff forced to Requeue semantics but with retry_at = now + delay) or StepCompleted(Err(Timeout)) when exhausted, flushes, and ends `Evicted{StepBackoff{retry_at}}` (retries) or `Evicted{External-like re-activate}` — choose and document: when attempts are exhausted the run must continue from replay, so end with an eviction that the executor re-activates immediately (add `EvictReason::StepTimedOut` if clearer; update outcome_code). Same for a per-step fuel breach: trap payload `StepFuelExhausted{seq}` -> record NonRetryable{kind:"fuel_exhausted"} -> evict for immediate re-activation. Investigate first (read wasmtime 50.0.2 source in ~/.cargo/registry for `epoch_deadline_callback` / `UpdateDeadline` and the 50 `StoreHookState` change); if the callback cannot see host state, keep the deadline in a field reachable from the store data `T` (HostState) — that is where the callback's `StoreContextMut<T>` points. Write tests first.
