<fjall_adaptation>
Locked (PROJECT.md "State store: redb vs fjall"): one atomic `WriteBatch` per apply batch with `applied_offset` in the batch, default buffered journal flush per commit, `persist(PersistMode::SyncAll)` checkpoint every 100 ms or 256 batches recording `checkpointed_offset`; recovery replays the WAL from the state's OWN `applied_offset` (after a process kill fjall can reopen AHEAD of the last checkpoint; that is safe because the state only ever applies WAL-durable commands). Bound journal/memtable to bound reopen time (S3 measured 3.2–3.4 s for ~540k un-flushed commands with the 512 MiB default). Keep the apply path to one point read per command plus an in-batch overlay (RMW margin over the 90k rule is only 1.19x).

Design choices made here (planner discretion, record in SUMMARY):
- **One fjall Database per partition** (`<data>/state/p{:04}`), not one per node: STOR-06's "delete a partition's state store" is `rm -rf state/pNNNN`; fjall poisons a whole Database on error, so per-partition DBs keep STOR-07 failures partition-local; journal replay on reopen is bounded per partition. Cost: P background pools → default `worker_threads = 1` per partition.
- Defaults (`StoreConfig::default()`): `worker_threads = 1`, `max_journaling_size = 64 MiB` (fjall minimum), `max_memtable_size = 8 MiB` per keyspace, `cache_size = 16 MiB`. All configurable; plan 02-16 measures reopen time / write stalls and may retune.
- fjall's `WriteBatch` has no read-your-writes → `ApplyBatch` keeps `BTreeMap<(TableId, Vec<u8>), Option<Vec<u8>>>` (None = tombstone). BTreeMap, never HashMap (determinism lint).
</fjall_adaptation>
