  <behavior>
    - In the commit callback, the order is fixed (W7): (1) lock `HwVector`, raise `v[p]` to `durable_end` (monotonic), release; (2) only then `send_if_modified` the HW watch. A comment states why: any task that observes HW ≥ x through the watch, and then appends to another partition, does so after x is in the vector, so a cut containing the second append also contains x.
    - `LogNode::cut()` clones under the lock: one uncontended lock per group commit and per cut.
    - Property test `hw_cut` (assumption stated in the test doc: the update-before-publish order above): 4 partitions, tasks that append to B only after observing A's HW ≥ x through the watch. For any cut taken concurrently, `cut[B] ≥ y` implies `cut[A] ≥ x`. 256 cases, plus a negative control: with a test-only flag that publishes first and updates after, the property is violated at least once in 10,000 iterations, or the control is documented as non-deterministic and skipped.
    - `read_envelopes(p, from, max_bytes)` is HW-capped and returns whole batches with the stored OSTR envelope bytes and their epoch. Test: byte-identity with `Envelope::encode` of the decoded commands from `read`; respects HW; batch boundaries are preserved across an epoch change.
    - Measure the per-commit overhead with the existing group-commit test and report it.
  </behavior>
