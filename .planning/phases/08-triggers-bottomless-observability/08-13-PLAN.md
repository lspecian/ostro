  <name>Task 1: OSEG chunks + manifest (validate) + LOCK fencing</name>
  <files>crates/ostro-backup/src/{chunk,manifest,fence}.rs, crates/ostro-backup/tests/fencing.rs</files>
  <behavior>
    - `chunk`: encode/decode OSEG v1. `verify_chain(start: ChainStart{base, prev_sha}, chunks)` checks prev links (the first chunk's prev = zero), `base == prev.end` (the first base == chain_start), non-decreasing epochs, each envelope's CRC32C (via the ostro-types envelope decoder) and the trailer sha. Unit tests cover corruption of the header, body, trailer, a chain break and a wrong start.
    - `manifest`: postcard + sha256 trailer, `prev_manifest_sha256` linking, `manifest/current` and `manifest/gen/<gen 20d>`. `Manifest::validate()` enforces the ordering in `<interfaces>` (B3/B4). Decoding a manifest that fails validation is an error; restore (08-18) calls the same function.
    - `fence`:
      - `acquire(store, ident{cluster_id,node_id,incarnation}, takeover)`: PUT `LOCK` with If-None-Match → Ok; if it exists with the same ident → Ok; with a different ident and `takeover` → overwrite via If-Match on its etag; otherwise `Fenced`;
      - `check_before_manifest` is a no-op when conditional PUT is supported, else it re-reads LOCK and compares (the fallback).
    - Immutable objects (W9): `put_immutable(store, key, bytes, sha)` uses `put_if_absent`. On PreconditionFailed it HEADs/GETs the existing object: the same sha → success (idempotent retry after a crash); a different sha → `Fenced` (another writer produced different bytes under our key).
    - `fencing` tests: two uploaders with different incarnations → the second is fenced; `takeover` works; the fallback path (conditional disabled) detects a LOCK change; the immutable put conflict → fenced; an identical re-put → ok. A MinIO variant is env-gated on the `OSTRO_TEST_S3_*` variables (Phase 6 convention).
  </behavior>

<task type="auto" tdd="true">
  <name>Task 2: Uploader::round + loop: chain start, snapshot hold-back, upload floor, remote retention, metrics</name>
  <files>crates/ostro-backup/src/uploader.rs, crates/ostro-backup/tests/common/mod.rs, crates/ostro-backup/tests/{uploader,cut_consistency,chain_start}.rs</files>
  <behavior>
    - `Uploader::round(&self, store) -> RoundReport`:
      1. **first** read `pairs_p = node.applied_state(p)` for every partition (08-08's atomic accessor), **then** `cut = node.log_cut()`, and record `cut_read_at`. Because apply only advances below HW and HW ≤ the cut read afterwards, `applied_p ≤ HW_p ≤ cut_p` holds by construction (W2);
      2. blobs: upload every pending blob (observer + a startup reconcile via `list("blobs/")`) with `put_immutable`;
      3. per partition, **chain start (B4)**: if there is no remote chain for p (fresh prefix) **or** `uploaded_end_p < log_start_p`, upload the newest local snapshot S with `S.applied_offset ≥ log_start_p` first (`p/<pppp>/snap/<applied 20d>-<sha256>.osnap`, multipart ≥ 64 MiB) and set `chain_start_p = S.applied_offset` with prev = zero. If no snapshot exists, `log_start_p` must be 0 and the chain starts at 0 with `snapshot_key = None`; otherwise the partition is skipped this round and `ostro_backup_failures_total{kind="no_snapshot"}` is incremented (the next local snapshot unblocks it);
      4. chunks `[uploaded_end_p, cut_p)`, split at epoch boundaries, ≤ 8 MiB per chunk, via `put_immutable`;
      5. snapshots (B3): any new local snapshot is uploaded with `put_immutable` as soon as it appears, but the manifest references only the newest uploaded snapshot with `snapshot_offset ≤ cut_p`. Later ones wait in a pending set until a later round's cut covers them;
      6. the meta snapshot if the meta applied index changed, captured after step 1;
      7. `verify_offset_p`/`verify_state_hash_p` = the pair read in step 1. If that applied offset is below the referenced snapshot's offset, use the snapshot's own `(applied_offset, state_hash)` instead (from its trailer). A test asserts `snapshot_offset ≤ verify_offset ≤ cut_offset` for every manifest written;
      8. build the manifest, call `validate()`, then `check_before_manifest`, the failpoint `upload::before_manifest`, and PUT `manifest/current` with If-Match on the previous etag, plus `manifest/gen/<gen>` via `put_immutable` on rounds that changed any snapshot.

      On a precondition failure: stop and set `ostro_backup_fenced = 1`. After a durable manifest: `upload_floor_p = min(referenced snapshot offset (or chain_start), uploaded chunk end)` via `floor_handles`. Then remote retention: keep the last `remote_snapshots_keep` referenced snapshots per partition and the chunks with `end > oldest kept snapshot offset`, and delete older ones (plus gen manifests older than the oldest kept snapshot round).
    - The loop runs every `seal_interval`; idle partitions upload nothing. Metrics:
      - `ostro_backup_cut_age_seconds` (now − cut_at of the last durable manifest);
      - `ostro_backup_upload_seconds` (round duration, W8);
      - `ostro_backup_upload_bytes_total{kind}`, `ostro_backup_failures_total{kind}`, `ostro_backup_fenced`;
      - `ostro_backup_upload_floor_lag{partition}` (applied − upload_floor, W13: a stuck floor blocks trimming).

      Failures back off and never block apply.
    - Tests on LocalFs (`tests/common` builds a Node + LocalFs store in a tempdir):
      - `uploader`:
        - only below HW (chunk end ≤ cut ≤ HW);
        - barrier closed / Inspect mode → zero objects;
        - keys and epoch split after a forced epoch bump;
        - blobs present before any chunk referencing them;
        - the meta snapshot comes after the cut;
        - the upload floor caps trimming;
        - **per tick, `cut_read_at − previous cut_read_at ≤ seal_interval + scheduling slack`, and the cut lag at manifest time minus the measured round duration ≤ seal_interval** (W8; the upload latency is reported separately in the SUMMARY).
      - `chain_start` (B4):
        - (a) a fresh prefix on a node with log_start = 0 and no snapshots → the chain starts at 0 and the manifest validates;
        - (b) **backup enabled on an already-trimmed node** (log_start > 0 with snapshots) → the first round uploads the newest snapshot, the chain starts at its offset, and a restore-style check (snapshot + chunks) reproduces the digest;
        - (c) **a retention pass before the first upload** does not trim (the floor initialised by 08-09), and after the first manifest trimming resumes up to the published floor;
        - (d) uploaded_end < log_start after a long outage → restart from a snapshot.
      - `cut_consistency` (proptest, 24 cases): a cross-partition children/signals workload; after each round, simulate "restore at this manifest" (truncate each partition's log at `cut_p` in a copy, install the referenced snapshot, rebuild) → for every pair (A, B), `outbox_next_seq[A→B]` and `inbound_seen_B[A]` are consistent. Plus a deterministic case (B3) where **a snapshot lands between reading the cut and writing the manifest** (injected through a test hook between steps 1 and 8): the manifest does not reference it, validation passes, and the simulated restore is consistent. The next round references it once the cut covers it.
  </behavior>
