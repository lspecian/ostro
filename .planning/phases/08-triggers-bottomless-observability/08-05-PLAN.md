  <behavior>
    Spike first (RED can be a compile test): confirm `jiff02::tz::TimeZone::tzif(name, bytes)` and `jiff::tz::TimeZone::tzif(name, bytes)` exist with those shapes, and that `croner::Cron::new(expr).with_seconds_optional().parse()` + `find_next_occurrence(&jiff02::Zoned, false)` compile under the jiff feature. If a shape differs, adapt the adapter and record it in the SUMMARY. If jiff02 has no bytes constructor, enable nothing new; use the closest API with the same bundled-bytes source, and document how equality of the rules is ensured.

    Cases (`expr`, tz, after (local time) → expected next, UTC):
    - `0 30 2 * * *`, America/New_York, 2026-03-08 00:00 → 2026-03-09 02:30 EDT. 02:30 does not exist on 03-08, so there is no fire that day (croner 4.0.3 DST-gap rule; assert whatever croner documents and pin it).
    - `0 30 1 * * *`, America/New_York, 2026-11-01 00:00 → exactly one fire at 01:30 EDT (first occurrence). The next is 2026-11-02 01:30 EST.
    - `0 0 2 * * *`, Europe/Berlin, around 2026-03-29 and 2026-10-25: same gap/overlap assertions.
    - `0 15 2 * * *`, Australia/Lord_Howe, 30-minute DST shift on 2026-10-04: pinned.
    - Seconds field `*/15 * * * * *`, `L` (`0 0 0 L * *`), `#` (`0 0 9 * * MON#2`), `W` (`0 0 9 15W * *`).
    - UTC and the empty timezone (default "UTC").
    - Errors: invalid expression → `CronError::Expr`; unknown tz `Mars/Base` → `CronError::Timezone`; `end_at_ms < start_at_ms` → `CronError::Bounds`.
    - `latest_at_or_before(spec, t) -> Option<i64>`: the latest fire ≤ t (within [start_at, end_at]). Use croner's previous-occurrence API if 4.0.3 has one (spike); otherwise an expanding backward window (1 min, doubling, never below the floor) followed by forward iteration with `next_after` inside the window. Bounded work regardless of how long ago the floor is.
    - `fires_in(spec, from_exclusive, to_inclusive, cap) -> (Vec<i64>, truncated)`: increasing fires in the range, keeping the **last** `cap` (a ring of size cap while iterating forward), so truncation drops the oldest, never the newest.
    - `plan_catchup(spec, watermark, created_at_ms, now, policy, window_ms, cap) -> CatchupPlan { fire: Vec<i64>, advance_to: Option<i64>, skipped: u32 }` with `floor = max(watermark, created_at_ms)` (W6):
      - Skip → `latest = latest_at_or_before(now)`; if `latest > floor`: `advance_to = latest`, `fire = []`, `skipped` = an estimate capped at u32 (count via `fires_in` only when cheap; otherwise saturate and document).
      - One → if `latest > floor`: `fire = [latest]`, `advance_to = None` (the Fire itself moves the watermark).
      - All → `fires_in(max(floor, now - window), now, cap)` → `fire` = the last `cap` fires, `advance_to = None`, `skipped` = the number of dropped older fires (the first Fire moves the watermark past them).
    - The driver's steady state restarts at `next_after(max(watermark, now))` (documented here for 08-14).
    - Cap test (consistent with 08-14): window 60 s, cap 3, a `*/10 * * * * *` schedule and 5 minutes of downtime → exactly 3 fires, and they are the **3 newest** fire times ≤ now.
    - Proptest (512 cases): random expr from a small grammar × tz from {UTC, NY, Berlin, Lord_Howe, Kolkata} × random after → `next_after` is strictly increasing when iterated 50 times, and `fires_in` equals the iterated `next_after` sequence (restricted to its last `cap` elements). A second proptest covers **downtime ≫ cap × period** (floor up to 30 days back, `* * * * * *`, cap ≤ 100): Skip/One return exactly `latest_at_or_before(now)`; All returns the last `cap` fires ≤ now, all > `now - window`; runtime per case stays under 50 ms.
  </behavior>
