    - `ServerEffectDriver` implements `ostro_engine::EffectDriver`:
      - `start` resolves the deployed module name for the run through the run's `WorkflowVersion.module` (05-07: the tenant-qualified deployed module name `<tenant>/<name>`, D23), looked up by the run's workflow + version and cached per (workflow, version). **Never** derive it from the sha-keyed, nameless `ModuleRecord`: a name there would let a second tenant uploading the same bytes rename the first tenant's module and tenant, builds `EffectBase{cluster_id, partition, run_id, attempt, module, tenant}` and calls `Bridge::start`;
      - `cancel` → `Bridge::cancel`.
    - `PartitionCompletionSink` implements `CompletionSink`. It takes `completed_at` = wall clock, builds the payload `complete_effect_payload(op, &outcome, completed_at_nanos)` (the encoded EffectCompleted event bytes, B2), runs `prepare_payload` on those bytes (inline ≤ 256 KiB, blob ref above), and submits `Cmd::CompleteEffect{run_id, op, outcome: Some(payload_ref), completed_at_ms}`. The test for a 1 MiB outcome (blob path) is in 06-15. Partition outcomes map to:
      - Accepted or Duplicate → Ok;
      - RunTerminal or RunNotFound → `Dropped`;
      - not-leader or unavailable → `Unavailable` (the driver retries).
    - `PartitionSendGate` implements `SendGate`: Abandon unless this node currently leads the partition **and** the run exists and is not terminal **and** `query::effect_row(run, op)` is `Some`.
    - `PartitionSink::effect_driver()` returns `Some(Arc<ServerEffectDriver>)` when BridgeServices exists.
    - **B1:** when BridgeServices exists, `unsupported_input` returns `None` for `EventBody::EffectScheduled` (make it a method, or pass a `bridge_enabled` flag). Both callers then skip effects: the post-append path, and **`repair_unsupported`, which runs on every journal load and would otherwise fail every in-flight effect after a crash or resume**. `ChildStarted` keeps its unsupported completion on both paths. Without BridgeServices (tests built without a bridge), behaviour is unchanged.
    - tests/sink.rs, with bridge enabled:
      - a journal ending in an uncompleted `EffectScheduled` → `repair_unsupported` appends nothing;
      - the same with a `ChildStarted` → ChildCompleted(unsupported) is appended;
      - with the bridge disabled, the old behaviour (an unsupported completion for both) is preserved.
    - derive.rs:
      - `EffectScheduled(op, request)` → `Derived::register_effect(op, EffectKind::from_request(&request), ts_ms)`;
      - `OpCancelled(op)` → `Derived::cancel_effect(op)` for every op that is not identified as a timer. CancelEffect is a blind delete, so it is harmless for other kinds; document this.

      The existing derive unit tests stay green, and new cases are added for both mappings.
    - After a successful append that included `CancelEffect`, the sink also calls `Bridge::cancel(partition, run, op)` (best effort). **Cancel on terminate:** calling `Bridge::cancel_run` when a run terminates is **best effort and optional**; this plan does not wire the executor module. The only guarantee is the SendGate check immediately before each send (terminal run or missing effects row → Abandon). It never goes through partition apply actions.
    - **Phase 8 tracing hooks (default no-op):** effects.rs defines `pub trait EffectHooks: Send + Sync` with default no-op methods, and `ServerEffectDriver` holds an `Arc<dyn EffectHooks>` (default `NoopEffectHooks`):
      - `fn decorate_live_request(&self, run: &RunRecord, op: u64, req: &mut ostro_types::journal::HttpRequest) {}` is called in `ServerEffectDriver::start` on the **live** `LiveEffect` copy only (the intent is already journaled), before `Bridge::start`, so the journal is unaffected;
      - `fn on_effect_complete(&self, run: &RunRef, op: u64, kind: EffectKind, started: SystemTime, ended: SystemTime, outcome: &RecordedResult) {}` is called by `PartitionCompletionSink` after submission. `started` comes from a `(run, op) → SystemTime` map recorded in `start`.

      Phase 8's 08-21 fills these in. There are no edits to ostro-bridge send.rs and no ostro-engine dependency in ostro-bridge. A unit test asserts the default no-op leaves the live request byte-identical (headers, url, body) and the journaled EffectScheduled unchanged.
