<task type="auto" tdd="true">
  <name>Task 2: Pools, exactly-once protocol, error mapping, DDL, GC (pool.rs, exactly_once.rs, gc.rs, mod.rs) + testkit db helpers</name>
  <files>crates/ostro-bridge/src/sql/pool.rs, crates/ostro-bridge/src/sql/exactly_once.rs, crates/ostro-bridge/src/sql/gc.rs, crates/ostro-bridge/src/sql/mod.rs, crates/ostro-testkit/src/db.rs, crates/ostro-bridge/tests/sql_pg.rs, crates/ostro-bridge/tests/sql_mysql.rs</files>
  <behavior>
    - `SqlConnector::new(meta, resolver, cluster_id, cfg)` implements `Connector` (kind Sql). `target()` = the connection name with its quota.
      - The module must be allowed the connection (`policy::allows_connection`, P-7) → else `egress_denied`; an unknown connection → `connection_unknown`.
      - Pools are built lazily per connection and rebuilt after `backend_ttl` or a config version change. Passwords resolve via `resolve_operator`.
      - On first build with `manage_schema`, run `CREATE TABLE IF NOT EXISTS <effects_table> (...)` **outside** any effect transaction. With `manage_schema=false`, the DDL is printed in the error/info log instead.
    - Exactly-once protocol, in this order:
      1. `BEGIN`;
      2. `INSERT` token(effect_key, run_id, op). On a unique violation (PG `23505` / MySQL `1062`): ROLLBACK, then `SELECT result`; NULL → `sql_exactly_once_violated`, else return the stored bytes **verbatim** as the outcome. The connector returns the decoded `OpOutput` from those bytes, and the test asserts `encode_outcome(decoded) == stored bytes`;
      3. `bridge_fail!("bridge::sql::before_user_stmt")`;
      4. the user statement via `sqlx::query` with binds, collecting rows up to max_rows/max_bytes (over → ROLLBACK → `response_too_large`);
      5. `UPDATE token SET result = encode_outcome(Ok(Sql(result)))`;
      6. `COMMIT`;
      7. **return the connection to the pool** (drop it), then `bridge_fail!("bridge::sql::after_commit")`. The failpoint must never hold a pooled connection (W4).

      **After COMMIT has been sent (B4):** a COMMIT error, a lost connection, or the `after_commit=return(error)` failpoint never completes Retryable. The connector runs a bounded **reconcile loop** with the same key (up to 5 attempts, backoff 200 ms → 5 s), each time on a fresh connection:
      - `SELECT result FROM token WHERE effect_key = $1`:
        - non-NULL → return the stored bytes (decoded to `OpOutput`; the completion bytes equal the stored bytes);
        - NULL → `sql_exactly_once_violated`;
      - no row (the COMMIT never landed) → re-run the full token protocol from step 1 (safe: nothing was committed).

      If the loop runs out, complete `NonRetryable{effect_outcome_unknown, details: {op, connection}}`; that is never re-sent. Errors **before** COMMIT (including 40001/40P01/1213/1205 during the statement) may stay Retryable.
    - **Re-drive horizon (W12):** when `effect.redrive` and `now - scheduled_ts > sql_effects_retention - 1h` (`[connectors] sql_effects_retention`, default 168h), complete `NonRetryable{effect_outcome_unknown, message: "re-drive older than the ostro_effects retention"}` without connecting. The token row may already have been garbage-collected, so running the statement again could duplicate it. Unit-test the decision function.
    - `exactly_once=false`: autocommit execution, at-least-once on re-drive (documented).
    - Errors before COMMIT: 40001/40P01/1213/1205 → `Retryable{kind: sql_error}` with sqlstate in details; others → `NonRetryable{sql_error, details: {sqlstate, message}}`. After COMMIT: see the reconcile loop above. The message is the DB error text with the connection URL redacted.
    - `gc.rs`: `SqlConnector::spawn_gc(retention)` deletes token rows older than retention in batches of 1000 per connection, every 10 minutes. It is cancellable.
    - `ostro-testkit::db`:
      - `pg() -> Option<PgTestDb>` (reads `OSTRO_TEST_PG_URL`, creates schema `t_<uuid simple>`, exposes `.schema()` for the connection config `schema` field, and drops the schema on Drop via a blocking cleanup thread);
      - `mysql() -> Option<MyTestDb>` (creates database `t_<uuid>`);
      - both print `SKIP: <VAR> unset (...)` and return None when unset.
    - Integration tests (identical cases for PG and MySQL):
      - token-first: insert a user row exactly-once, re-run the same (run, op) → the stored result is returned and the user table has 1 row;
      - NULL result → violated;
      - `ALTER TABLE` exactly-once → rejected and nothing runs;
      - deadlock/serialization mapped to Retryable (force with two transactions);
      - cap → `response_too_large` with no token row left;
      - the value round-trip of every SqlValue arm;
      - GC deletes old rows;
      - with the `failpoints` feature: `bridge::sql::after_commit=return(error)` → the connector's **own** reconcile loop returns `Ok` with bytes equal to `ostro_effects.result`, and the user table has exactly 1 row. The test asserts the outcome is Ok (never Retryable) and byte-equal to the stored result (B4);
      - pool size 2 with 10 exactly-once effects all hung at `after_commit=return(hang)`. The failpoint is process-wide and only on the exactly-once path, so an 11th exactly-once effect would hang too. Instead: (a) poll the DB until all 10 token rows have a non-NULL `result` (all 10 committed, which is only possible with a 2-connection pool if each connection was returned before the failpoint); (b) an 11th statement with `exactly_once=false` completes. The autocommit path does **not** pass through `bridge::sql::after_commit` (that site is exactly-once only; document it in sql/mod.rs) (W4);
      - `schema` config: two connections pointing at two different `t_<uuid>` schemas see only their own tables (W3);
      - a re-drive with `scheduled_ts` older than retention − 1h → `effect_outcome_unknown` and no DB round trip (W12).
  </behavior>
