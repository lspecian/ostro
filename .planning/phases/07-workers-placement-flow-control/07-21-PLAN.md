`fencing_chaos.rs` (`#[cfg(feature = "failpoints")]`, `#[ignore]`):
- Env: `OSTRO_CHAOS_RUNS` (default 10000), `OSTRO_CHAOS_SHARDS` (default 20), `OSTRO_CHAOS_PARALLEL` (default 4), `OSTRO_CHAOS_STATE_DIR` (default `target/fencing-chaos`), `OSTRO_CHAOS_SEED`; modes `campaign` (run pending shards) and `report` (aggregate).
- Per shard: one server (lease_ttl 3 s, a workers queue + an auto queue with spill knobs from 07-13) + 3 workers + its own MockProvider; submit runs/shard `pay-flow` runs with distinct keys; a fault driver (seeded) injects every 2–5 s one of: kill -9 a random worker (restart it); SIGSTOP a random worker for lease_ttl + 0–2 s then SIGCONT; enable a `worker::` failpoint (pause/return error) on one worker for a window; enable an executor/dispatcher failpoint on the server; kill -9 the server and restart it on the same data dir (workers reconnect). Log every fault with a timestamp.
- After all runs reach a terminal state (bounded wait), assert per shard:
  - `charges(key) == 1` for every key; every run Completed with the charge recorded in its result; no run lost.
  - **fenced_sends == 0**, where a fenced send is defined (W5) as: a mock request for key K that arrives after a StartEffect for K was rejected by the leader (lease/auth check), with **no leader kill between that rejection and the request**. Correlate the server's StartEffect-rejection log (run, op, key, time) with the mock's request log (key, arrival time) and the fault log.
  - **Duplicate attribution (W5):** for each key with `requests(key) > 1`, the duplicate is attributed to (a) a leader kill whose timestamp lies between the key's first request and its `effect_completed`, or (b) a 409-in-progress retry **only if** the leader's bridge logged an `http_retry` for the same registry entry (partition, run, op) at that time. Anything else is unattributed and fails the shard.
  - **raw_duplicates == 0** in every shard (or time window between faults) that contains **no leader kill** (W5): worker/executor zombies alone must never produce a second raw request.
- Write `shard-NN.json` (counts, faults, durations, duplicates with attribution); `report` aggregates into `report.json` with at least the top-level integer keys `runs`, `completed`, `double_charges`, `lost`, `fenced_sends`, `raw_duplicates`, `raw_duplicates_without_leader_kill`, `unattributed_duplicates` and a `faults` object by kind (pretty-printed as `"key": value`, which the plan's verify greps) and prints a summary table (runs, faults by kind, charges==1 count, duplicates attributed by cause, max/median run latency).
